with these exact signatures (Task 6 calls them):

```go
type JudgingSession struct {
	ChannelId, WorkspaceId, DagORef string
	Role, Label, Tree, Prompt       string

}
func LaunchJudgingSession(ctx context.Context, s JudgingSession) (string, error)
```

  `LaunchJudgingSession` with `DagORef: g.OID`, then appends `RunEventKindStageSessionStarted` as today.
- `stageSessionLost` becomes a call to `JudgingSessionLost(ctx, g.ChannelId, ...)`.

### Task 6: Launch, watch and deliver the builder check on the server
**Depends on:** Task 1, Task 2 (calls LaunchJudgingSession and JudgingSessionLost), Task 3 (calls Decide, Prompt, ReportPath and Line)
**Files:** `pkg/wshrpc/wshserver/wshserver_brainstorm.go`, `pkg/wshrpc/wshserver/wshserver_brainstorm_test.go`, `pkg/wshrpc/wshserver/wshserver_runs.go`, `pkg/wshrpc/wshserver/wshserver_run_test.go`, `cmd/server/main-server.go`

D1, D3, D4 (workspace, channel, the seal), D5, D6, D8. Replaces Task 1's stub in `wshserver_brainstorm.go`.

- `BrainstormCheckCommand` validates the request. A block and a file are given. The file parses as JSON and its
  `spec` names a file that exists, relative to the brainstorm's project (the directory above `.superpowers`). The
  block's tab is found. The tab's `brainstorm:checkstate` is not `reading`; if it is, the error is "a builder check
  is already running". It then writes `reading` (all five keys, D5) and returns. The watcher runs in a goroutine on
  a detached context.
- The route, D3's whole chain. First the resolved profile's `ReviewerRoute`
  (`jarvis.ResolveProfile(jarvis.LoadGlobalProfile(), jarvis.OverrideFromMeta(ch))`) when it names a runtime or a
  model. Else the tab's `session:agent` runtime with its default model, when that harness can run a worker. Else
  `runroute.DefaultRuntime("")` with its default model. The launch therefore never gets an empty route.
- The watcher takes the channel with `wstore.EnsureChannelAtPath(ctx, <project name>, <project dir>)`, where the
  project name is the tab's `session:project`, else the directory's base name. The workspace is the one that holds
  the agent's tab. It calls `orchestrate.LaunchJudgingSession` with Role `jarvis.UsageRole_BuilderCheck`, Label
  `Builder check · <title>`, Tree = the project dir, and a report path in `os.TempDir()` named by a fresh uuid. It
  records `checkrun` and `checkchannel`.
- The watcher then ticks every `builderCheckPollEvery` (5 s) through `brainstormcheck.Decide`, using
  `orchestrate.JudgingSessionLost` with the record's `checkts`.
  - Deliver: write `Run.Report` to `ReportPath`, send `Line` with `deliverAgentMessage(blockId, ...)`, and set
    `answered`.
  - Fail: stop the session (`stopStageSession`) and set `failed` with the reason.
  - A launch error, or a report write error: set `failed` with "Arc could not start the builder: <err>" or the
    write error.
  - Every meta write broadcasts the tab's WOS update.
- `ResumeBuilderChecks(ctx)` is the startup sweep (D6), called once from `cmd/server/main-server.go` after the store
  is up. A `reading` tab with a `checkrun` gets its watcher re-armed. One without a `checkrun` is set to `failed`,
  "Arc restarted before the builder started."
- `wshserver_runs.go`: `advanceRun` leaves `sealDue` false for a builder-check run (D4). Everything else on its done
  path stays as it is.
- Seams for the tests: the launch, the run read, the prompt delivery and the stop are package vars, as
  `stopStageSession` is today.

Acceptance: `go test ./pkg/wshrpc/wshserver -run 'BrainstormCheck|BuilderCheck'` covers:
- the handler's refusals: no file, no spec, a missing spec file, already reading;
- a launch writing `reading` and then `checkrun` / `checkchannel`;
- the route chain: the profile's reviewer route; then `session:agent` = pi; then no `session:agent`, which falls to
  the default runtime;
- a done run with a report writing the file, delivering the line to the agent's block, and setting `answered`;
- a lost run stopping the session and setting `failed` with the reason;
- a launch error setting `failed`;
- the sweep re-arming a reading check that has a run, and failing one that has none;
- a done builder-check run leaving `sealDue` false.

### Task 9: The CDP scenario
**Depends on:** Task 7 (drives the pane states and data attributes it adds)

Add the scenario `brainstorm-builder-check` beside `brainstorm-builder-ask`, reusing its arrange and teardown
helpers (`bsArrangeAgent`). It plays the server's side by setting the five tab meta keys on the agent's tab (a
`setmeta` RPC on `tab:<id>`, as other scenarios in `scenarios.mjs` do). It plays the agent's side by writing

2. "pending": `checkstate=reading`: `[data-brainstorm-check-pending]` reads "A builder is reading the design.",
   and Check with a builder is absent or disabled.

   with the agent played as idle: the check view shows the builder's question and the pending card is gone.
5. "failed": the file's `check` is reset to null, `checkstate=failed` with a reason:
   `[data-brainstorm-check-failed]` shows the reason and Try again.
6. "retry": pressing Try again sends `brainstorm: check` to the agent's terminal, asserted the way the existing
   scenarios assert a sent line.
