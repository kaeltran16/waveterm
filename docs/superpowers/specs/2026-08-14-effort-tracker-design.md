# Effort Tracker — Design

**Date:** 2026-08-14
**Status:** Approved (design review 2026-08-14; FE design settled in the visual-companion session, same day)
**Type:** Feature design
**Scope:** Wave backend (`wavesrv` + `wsh`) — the Effort object, its RPC surface, and the agent API. The briefing/detail UI is designed alongside (see UI section) and refined separately in the visual companion.

## Problem

Big efforts — a migration, an enablement rollout, a multi-week refactor — are too large for one Run. Today the only way to track them is a hand-maintained markdown "meta spec" in the repo (e.g. `2026-07-10-scenario-gate-clearance-meta-spec.md` in the SIEM repo): an ordered list of phases with status marks, owners, and dated annotations. That file exists only because Wave has no alternative. The briefing shows the work's *parts* (runs, blockers, agents) but never the *whole* — no sequence, no done/total, no trail.

This design adds a first-class **Effort** object: a Wave-owned tracker with ordered chunks (phases), statuses, owners, and an append-only note trail. Both humans (briefing UI) and agents (`wsh effort …`) read and write it through the same RPCs. The meta spec's role — sequence, status, trail — moves into Wave; reference procedures (preconditions, rollback) stay in linked docs.

## Object model

New registered `waveobj` type `Effort` (OType `effort`), stored in wstore like Run/Channel. JSON tags as written; TS bindings generated by `task generate`.

```
type Effort struct {
    OID         string       `json:"oid"`
    Version     int          `json:"version"`
    Title       string       `json:"title"`
    Project     string       `json:"project,omitempty"`  // free string; "" = unscoped
    Ticket      string       `json:"ticket,omitempty"`    // free string (e.g. "SIEM-1662")
    Status      string       `json:"status"`              // active | paused | done | archived
    ParentOID   string       `json:"parentoid,omitempty"` // optional parent effort (tree link, one level)
    Chunks      []EffortChunk `json:"chunks"`             // ordered; may be empty (agents create the effort first, plan chunks after)
    Notes       []EffortNote `json:"notes,omitempty"`     // effort-level trail
    CreatedTs   int64        `json:"createdts"`
    UpdatedTs   int64        `json:"updatedts"`           // bumped on every mutation
    Meta        MetaMapType  `json:"meta"`
}

type EffortChunk struct {
    Label     string       `json:"label"`              // unique within the effort; reference key
    Status    string       `json:"status"`             // pending | active | done | deferred | blocked | skipped
    Owner     string       `json:"owner,omitempty"`    // free string
    Notes     []EffortNote `json:"notes,omitempty"`    // chunk-level append-only trail
    UpdatedTs int64        `json:"updatedts"`
}

type EffortNote struct {
    Ts   int64  `json:"ts"`
    Text string `json:"text"`
}
```

Decisions:

- **Notes are append-only trails** (effort-level and chunk-level), never a single editable field. Every status mutation auto-stamps (`"marked done"`), agents and humans append annotations (`--note`). This preserves the meta spec's dated-annotation behavior without hand-maintained dates.
- **Chunk labels are unique per effort.** Agents reference chunks by label or 1-based index; ambiguity is a hard error. Enforced at validation, not by UI convention.
- **Statuses:** `pending | active | done | deferred | blocked | skipped`. `deferred` and `blocked` are distinct (the enablement tracker used both: deferred-to-deployment vs blocked-on-substrate); `skipped` covers "decided not to do".
- **Tree links:** `ParentOID` is the only link v1. `effort link` / `effort unlink` set/clear it. Self-link rejected; deeper validation (cycles) deferred — a two-level tree is the target use ("program" → sub-efforts), and v1 trusts the creator.
- **Delete is real delete** (guarded). Archive is a Status, not a tombstone.

## RPC contract

Two commands (registered in wshrpc + wshclient generated):

### `EffortCreateCommand`

```
{ title: string, project?: string, ticket?: string, chunks: [{label: string, owner?: string}], parentoid?: string }
→ { effortoid: string }
```

Validation: title non-empty (≤ 200 chars); chunk labels non-empty, unique, ≤ 200 chars; ≥ 1 chunk unless the caller intends to add them later (allowed: zero chunks — agents often create first, plan chunks after brainstorming). Parent must exist and not be self.

### `EffortMutateCommand` — one RPC, typed op union, atomic

```
{ effortoid: string, ops: [{op, …}], note?: string }
```

`note` at command level is appended to the affected chunk (or effort) trail as the op's auto-stamp text when the op has no `--note`-equivalent. Each op:

| op | fields | effect |
|---|---|---|
| `rename` | title | retitle effort |
| `setProject` | project ("" clears) | |
| `setTicket` | ticket ("" clears) | |
| `setStatus` | status | effort-level active/paused/done/archived |
| `link` | parentoid | set ParentOID ("" = unlink) |
| `addChunk` | label, at?, owner? | insert chunk (default append) |
| `removeChunk` | chunk | delete chunk (guarded: cannot remove the last chunk of a non-archived effort) |
| `renameChunk` | chunk, label | |
| `moveChunk` | chunk, at | reorder (1-based) |
| `setChunkStatus` | chunk, status, note? | status change + auto-stamp |
| `appendNote` | chunk?, note | chunk note (or effort note when chunk omitted) |
| `setOwner` | chunk, owner ("" clears) | |
| `advance` | note? | active chunk → done; marker moves to the first non-done chunk (pending/blocked/deferred order: first by position) |
| `reopen` | chunk | done → active (undo advance; sets the chunk active) |

Rules:

- `chunk` refs accept a label (exact) or 1-based index; ambiguous or unknown → hard error naming the candidates.
- Ops run as one atomic write: all validate, then apply; a failing op aborts the whole command (no partial apply). Multiple ops in one command apply in order.
- Every mutation bumps `Version` and `UpdatedTs` and auto-stamps the affected trail.
- **Concurrency: last-write-wins.** Version is bumped, not CAS-checked. Two agents ticking concurrently may drop a note; acceptable v1 (rare, and the trail keeps the rest).
- Errors: `EC_UNKNOWN_EFFORT`, `EC_UNKNOWN_CHUNK`, `EC_AMBIGUOUS_CHUNK`, `EC_INVALID_STATUS`, `EC_DUPLICATE_LABEL`, `EC_LAST_CHUNK`, `EC_BAD_PARENT` — each with a human-readable message including context (effort title, chunk candidates).

## WorkState leg

`FetchWorkState` gains an efforts leg (all non-archived efforts, newest-updated first):

```
efforts: [{
  oref: "effort:<oid>", title, project?, ticket?, status,
  parentoid?,
  chunks: [{label, status, owner?, workrefs: [{kind, oref}]}],  // no note trails — summary only
  done: n, total: n,                          // done = chunks with status "done"
  activeChunk?: label,                        // first chunk with status "active", else first non-done
  updatedts
}]
```

Delta event kinds (shown in "Since last visit", navtarget = `effort:<oid>`):

- `effort-created` — "Effort created · N chunks"
- `chunk-done` — "Chunk done · <label>"
- `chunk-added` — "Chunk added · <label>"
- `chunk-status` — "Chunk <label> · <status>"
- `effort-status` — "Effort <status>"
- `effort-note` — "Note · <chunk|effort>"

All efforts (including archived) remain queryable via `wsh effort show <oid>`; only non-archived flow into WorkState.

**Capping.** The efforts leg is bounded by effort count, not time: chunk summaries only (label/status/owner/workrefs) — note trails never cross the wire; they are fetched per effort on demand via `wsh effort show`. Effort delta events ride the same ≤7-day window as every other leg. The pre-existing unbounded legs (all-runs DB read, full vault query) are unchanged and tracked as an adjacent optimization, not part of this feature.

**Delta row shape.** title = event wording ("Chunk done · <label>"), meta line = the effort title (e.g. title "Chunk done · Phase 3", meta "Scenario gate clearance").

## Agent API — `wsh effort`

`cmd/wsh/cmd/wshcmd-effort.go` (+ tests), sibling of the `jarvis` group. Every state-returning command supports `--json`. `effort` refs accept the oid; `chunk` refs accept label or 1-based index.

```
wsh effort create <title> [--project P] [--ticket T] [--chunk "<label>" ...] [--parent <effort>] [--json]
wsh effort list [--project P] [--json]                # oid, title, project, ticket, status, done/total, active chunk
wsh effort show <effort> [--json]                     # full: chunks + statuses + owners + full note trails + parent
wsh effort rename <effort> <title>
wsh effort project <effort> <P|"">
wsh effort ticket <effort> <T|"">
wsh effort status <effort> <active|paused|done|archived>
wsh effort link <effort> --parent <effort>
wsh effort unlink <effort>
wsh effort delete <effort> [--force]                  # refuses unless status=archived or --force
wsh effort chunk add <effort> "<label>" [--at N] [--owner X]
wsh effort chunk rename <effort> <chunk> "<label>"
wsh effort chunk move <effort> <chunk> <at>
wsh effort chunk remove <effort> <chunk>
wsh effort chunk status <effort> <chunk> <pending|active|done|deferred|blocked|skipped> [--note "..."]
wsh effort chunk note <effort> <chunk> --note "..."
wsh effort chunk owner <effort> <chunk> <owner|"">
wsh effort advance <effort> [--note "..."]
wsh effort reopen <effort> <chunk>
wsh effort chunk attach <effort> <chunk> --run <oid> | --agent <tabid>    # record workref (agents attach their own session to claim a chunk)
wsh effort chunk detach <effort> <chunk> --run <oid> | --agent <tabid>   # remove workref
```

`--json` output shape (stable contract for agents):

```
{ "ok": true, "effort": { "oid", "title", "project", "ticket", "status", "parentoid",
  "chunks": [{ "label", "status", "owner", "notes": [{"ts","text"}], "updatedts" }],
  "notes": [...], "done": n, "total": n, "createdts", "updatedts" } }
```

Errors exit non-zero with the RPC error message on stderr; `list`/`show` never print human tables when `--json` is set.

## UI — the complete feature

Four v1 surfaces, all calling the same two RPCs. The visual design was settled in the visual-companion session `.superpowers/brainstorm/3293-1786682951/content/` (`status-tone-language.html` = tone mapping decision, `briefing-layout-compare.html` = layout decision, `card-to-inline.html` = the card→expand interaction, `full-briefing-effort.html` = the complete page, `effort-create-app-language.html` = creation); the original brainstorm mockups live in `.superpowers/brainstorm/978-1786678832/content/`. The contract below is normative.

**Design language.** Every element maps to existing @theme tokens; no new primitives beyond the progress bar. Chunk-status tone language (locked as option B, matching the app's `statusChip` semantics — amber is the attention tone and is never used for "in progress"):

| Status | Tone | Mark |
|---|---|---|
| done | success (`bg-success/15 text-success`) | ✓ |
| active | accent (`bg-accent/15 text-accent-soft`, ring) | ▶ |
| blocked | asking/amber (`bg-asking/15 text-asking`) — blocked chunks also fold into the briefing's "Needs you" banner | ! |
| deferred | dashed `border-edge-strong`, muted | ⏸ |
| skipped | strikethrough muted | – |
| pending | plain `bg-surface-raised text-muted` | · |

**1 · The briefing (layout B — cockpit-grid pattern, approved).** Effort cards float full-width on top (top 6 by updated), Active work + Since last visit/Shipped fill two independent columns below, the Ask answer spans full width above the composer. Active work keeps its Runs / Blocked records / Direct agents subsections as mono sub-labels inside the left column. Every section has a hard display budget; overflow is a link, never a longer page:

| Section | Display cap | Overflow |
|---|---|---|
| Efforts | all non-archived (top 6 by updated) | "N more" → efforts list |
| Chunk chips | 12 chips, then one count chip ("+5") | inline expansion |
| Active work | 8 rows | "N more" → channel |
| Since last visit | 10 rows, grouped by day | "see all" → drill-down |
| Shipped · 7 days | 8 rows | "N more" → channel history |

Effort card (resting): title + ticket/project tags, progress bar, chunk chips (tone language above; chip text = chunk label), parent chip when linked, copyable agent handle (`wsh effort show <oid>`).

**Card → inline tracker (approved interaction).** Clicking the card (or a chip) expands it in place — no Stage navigation for the everyday path. The expanded card shows chunk rows (mark + label + latest note + status chip on one line each), the "Mark active chunk done" advance button (app primary), and + chunk / note actions; "▾ collapse" restores the card. A chip click expands and scrolls to that chunk's row. Hovering a row reveals its full trail; done rows offer reopen on hover. One effort expanded at a time. The subjects column gains an Efforts group — the effort subject lives there, and clicking it jumps to the briefing with that effort expanded.

**Progress math.** done / (total − skipped): skipped chunks shrink the denominator so an effort that finishes by skipping still reaches 100%. The count line shows "x of y · n skipped" only when n > 0. Deferred counts as remaining work. Edge: all chunks skipped → full bar, "all skipped".

**2 · Creation.** "+ Effort" in the briefing header opens a form: title, project, ticket, optional parent, chunks as a paste-and-tick list (one line per chunk; ticked lines become status=done at save) with a live parse hint ("8 chunks · 2 already done"). App input styling (`border-edge-mid bg-background`, mono uppercase labels). Maps 1:1 to `wsh effort create` flags.

**3 · Efforts list (overflow destination).** With more than 6 efforts, the briefing's "N more" link opens a Stage subject listing all efforts newest-updated first; clicking one navigates to it (expanded in the briefing). Minimal list, no management ops.

**4 · Effort detail (Stage subject).** The full record — all note trails, owners, workrefs ("loom working here" as an accent-soft mono line under the chunk's sub-line), edit ops — one click from the expanded card's header. Same chunk-row anatomy and tone language; trail display = latest inline, full trail on hover or the active chunk.

**5 · Launch-modal / composer pickers — deferred to a second UI slice.** Agents claim chunks via the CLI meanwhile (`wsh effort chunk attach --run <oid> | --agent <tabid>`). When the pickers land they add: an effort → chunk selector on the launch modal and in the run composer (`RunEffortRef` on the run), chunk context folded into the launch task, and a "Mark chunk done" offer on the agent card / evidence-sealed completion view. Detach on tick or session end (agent-hook SessionEnd); nothing auto-ticks.

## Deferred (explicit non-goals)

- **MCP tool wrapping the API** — wsh is the shim (ambient via WAVETERM_WSHBINDIR / PATH); an MCP surface adds no capability and arrives only if some agent cannot shell out.
- **Due dates**, effort comments-as-threads, cycle detection beyond self-link, CAS on writes.
- **Effort ordering pins** in the briefing (pinned efforts float to top) — follow-up if usage warrants.
- **Launch-modal / composer effort pickers** — second UI slice (UI §5); agents claim chunks via CLI attach meanwhile.
- **Bounding the runs + dossiers WorkState legs** (unbounded DB reads today, windowed only in the derived legs) — pre-existing; adjacent optimization, not this feature.
